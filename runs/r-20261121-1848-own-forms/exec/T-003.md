## Deviations
1. D-7 overrides plan section 3 step 5: one trigger `forSpreadsheet(inboxId).onFormSubmit()` instead of two form
   triggers, so the plan.json bullet "2 triggers" is "1 trigger" by design. The form is found from
   `e.range.getSheet().getFormUrl()` (edit-URL id, fallback `FormApp.openByUrl`), not `e.source`.
2. FR-01c overrides the plan.json bullet "replyTo omitted for `a@b.com\nBcc: x` and empty": both emails are invalid and
   email is required in both forms, so these replies send **no mail at all** (so no replyTo either). The replyTo check
   still exists in `fsBuildMail_` (strict regex), but every mail that reaches it has a valid email.
3. Values are read from `e.range` plus the header row (not `e.response`, which a spreadsheet trigger does not get). Items
   are matched by stored item id (`FS_ITEMS_<form>` property) -> current item title -> sheet header, then the spec label.
4. Setup also repairs item title, required flag, help text, choices and "Other" option by stored id, logging each fix
   (FR-07a); items are still never deleted or reordered.
5. Action-URL id length bounded to 20..120 (plan said 20+) to match the T-004 bound in FR-04a.
6. Cleaning also strips U+2028/U+2029 (not in FR-02b's list; stricter).
7. If the script lock cannot be taken within 20 s, the reply gets no email (row kept, fixed log line), rather than an
   uncounted send.
8. The Write tool turned `\uXXXX` escapes into literal invisible characters (which broke a regex); both files were
   re-escaped to pure ASCII with a one-off script in the scratchpad (not in the repo). Both files are ASCII-only now.

## Security fix FI-1 (reopened from security/impl-review.md)

Problem: the trigger's Song Database guard compared against `getActiveSpreadsheet()`. Inside an installable onFormSubmit
trigger on the inbox, that call may return the inbox itself, so every reply would be blocked, and the formula
neutralizer (which ran after the guard) would never run.

Changes (same write scope):
- `apps-script/FormsSetup.gs`: new constant `FS_PROP_SONG_DB = 'FS_SONG_DB_ID'`. `setupDanyelOzForms` stores the container
  id (from `getActiveSpreadsheet()` in the editor run; falls back to the stored value) in that Script Property, and its
  setup guards use it. `fsOnFormSubmit` now runs `fsNeutralize_(e.range)` first, right after the real-event check
  (FR-09), before any guard or validation return. It then reads `FS_SONG_DB_ID`: if that is missing, it logs
  `fsOnFormSubmit: Song Database id missing, run setupDanyelOzForms; no email` and returns (row kept, no mail). The guard
  compares the event's spreadsheet (`e.range.getSheet().getParent().getId()`) with the stored inbox id and the stored
  Song Database id. The trigger never calls `getActiveSpreadsheet()`.
- `tests/unit/test_formssetup.js`: setup stores `FS_SONG_DB_ID = SONGDB_ID`. New cases:
  1. getActiveSpreadsheet() returns the inbox during the trigger -> `=3` rewritten, 1 mail.
  2. The event spreadsheet is the Song Database -> `=1` rewritten, 0 mails, "inbox guard" logged.
  3. FS_SONG_DB_ID missing -> `+1` rewritten, 0 mails, the missing-id line logged.
  4. A reply in some other book is now neutralized too (`=2` rewritten), 0 mails.
  This replaces the old assertion that the other book stays untouched; the coordinator asked for the neutralizer to
  run first in every case.

## QA fix D-1 (S3, from qa/T-009.md)

Problem: after FI-1 the trigger rewrote formula cells before checking which spreadsheet the event came from. That meant
an event from the Song Database rewrote Song Database cells.

Change (same write scope):
- `apps-script/FormsSetup.gs` `fsOnFormSubmit`: the inbox guard runs first. It needs the event spreadsheet id to equal
  the stored `FS_INBOX_SHEET_ID` and to differ from `FS_SONG_DB_ID`. Any other spreadsheet (the Song Database, an
  unknown book, or no inbox id stored) is not touched, gets no email, and logs "inbox guard". The formula rewrite then
  runs on the inbox row before any other return. FI-1 behaviour is unchanged: the trigger never calls
  getActiveSpreadsheet(), the active=inbox case rewrites and mails, and a missing `FS_SONG_DB_ID` still rewrites the
  inbox cells but sends no email.
- `tests/unit/test_formssetup.js` now checks four cases:
  1. A reply in another book: cells untouched, 0 mails.
  2. Song Database event, with the inbox id wrongly set to the Song Database: cells untouched, 0 mails.
  3. Song Database event, with the correct inbox id stored: cells untouched, 0 mails.
  4. Inbox id missing: cells untouched, 0 mails.
  The existing FI-1 cases still pass.
