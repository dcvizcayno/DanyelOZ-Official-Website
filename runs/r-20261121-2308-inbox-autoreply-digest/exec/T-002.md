## Deviations
1. Names follow the charter G1 API (previewOldRows/deleteOldRows(token,count), installInboxTriggers/removeInboxTriggers,
   ibDailyDigest), not the design-review names (ibRetentionPreview, ibInstallTriggers, ibDigestTick).
2. IR-01 test vector: `v+1@gmail.com` normalises to `v@gmail.com`, not `v1@gmail.com` (the +tag is dropped, as IR-01a
   says), so the test uses `v1+a@gmail.com`, `V.1@googlemail.com`, `v1@gmail.com` -> 1 send. QA should use the same vector.
3. Closing line: the IR-01f footer is used verbatim in all 10 (the task's "If you didn't send this message, you can ignore
   this email" is its meaning; security asked for the exact text and QA greps it). It names danyeloz.info as plain text.
4. One subject per set (IR-14 "constant subject per set"); each template object still carries subject + body.
5. Template number is stored in auto_reply_at as "<ISO> #n" (no third column); getInboxData splits it into
   autoReplyAt / autoReplyTemplate.
6. Digest sync lines show "Sync request, <first name>, <age>" without songs (IR-11 overrides the charter's "topic or song").
7. Retention token: IR-09 asks for a refusal when a 4th row ages in, so the delete recomputes with a fresh cutoff and the
   token only proves a recent preview (15 min). previewOldRows also returns cutoffIso.
8. IB_QUOTA_FLOOR is the literal 46 (test asserts = FS_MAX_MAIL_PER_DAY + 1 + FS_MIN_QUOTA): top-level constants must not
   read another file's constants because Apps Script file load order is not guaranteed.
9. Rows already marked Replied or Done get no auto-reply; test sends use subject prefix "Test: " and greet "Hi Daniel,".
10. Charter C-1 Reply/mailto and the text-only DOM are the screen task; server returns fsClean_ strings cut to FS_FORMS max
    and emailOk = FS_EMAIL_RE on the raw value with no stripped characters.

## Follow-ups / residual risk
- Trigger handlers are public (Apps Script needs them without "_"): a page caller other than Daniel is ignored when
  Session shows another address, but a consumer-account stranger shows '' (same as a trigger), so in "Anyone with Google
  account" mode a stranger could fire ibAutoReplyTick early; it still obeys switch, caps, 30-day rule and floor. Security to judge.
- Columns are matched by the FS_FORMS label only (not by stored item id like fsReadAnswers_); a question renamed in the
  Form makes that field empty, so the row fails fsCheck_ and gets no reply (fails closed). setupDanyelOzForms repairs titles.
- Digest releases come from getSongs() (active Song Database in a time trigger of the bound script); any error -> no
  release lines, logged as a fixed string.
- SETUP.md / Calendar permission text and the human residual line (design review section 5) belong to other tasks.

## Fix: owner check

Defect: ibOwner_ compared Session.getActiveUser() with FS_NOTIFY, so Daniel would be locked out if the account that owns
the script is a different address.
Change (apps-script/Inbox.gs): new ibUsers_() reads the active user and Session.getEffectiveUser(), trimmed and lower-cased.
ibOwner_ allows only when both are non-empty and equal, and refuses everything else, blanks included. No address is
hardcoded in the check. ibTriggerUser_ (trigger handlers) now allows an active user that is blank or equal to the
effective user, and no longer compares against FS_NOTIFY. FS_NOTIFY is still used only as the mail target and reply-to,
and in the skip list.
Tests (tests/unit/test_inbox.js): the effective user is mocked as owner.account@gmail.com.
- Owner with mixed case allowed: getInboxData and installInboxTriggers work.
- FS_NOTIFY as the active user, when it is not the owner, is refused.
- Stranger and blank active user refused for all 9 API functions, with zero writes (existing loop).
- Blank effective user refused whatever the active user is.
- A handler called by another signed-in user does nothing.

## Security fix NF-01/NF-02

NF-01 (apps-script/Inbox.gs `ibOwner_`): allows only when Session.getActiveUser().getEmail() is non-empty and equals,
ignoring case, SpreadsheetApp.getActiveSpreadsheet().getOwner().getEmail(), the owner of the bound Song Database (no new
scope). It refuses when the owner is blank, null or throws, and on any error. No address is hardcoded. The
active == effective rule and `ibUsers_` are removed, so helper mode (active == effective == helper) is refused.
NF-02: `ibAutoReplyTick(e)` and `ibDailyDigest(e)` call `ibFromTrigger_(e, handler)`. A handler runs only if `e.triggerUid`
matches getUniqueId() of a project trigger for that same handler. Otherwise it logs a fixed line ("<handler>: not called
by its trigger, nothing done"), holding no personal data, and does nothing. `ibTriggerUser_` is removed.
docs/SETUP.md:122: now says that only the Google account that owns the Song Database can use the screen, also in helper
mode, and that this does not protect against Editors (FR-08 rule still holds).
Tests (tests/unit/test_inbox.js):
- Owner check:
  - The owner, owner.account@gmail.com (not FS_NOTIFY), is allowed in any case.
  - A stranger, a blank active user and helper mode are each refused on all 9 functions, with nothing written and no mail.
  - A blank, null or throwing owner is refused.
  - FS_NOTIFY is refused when it is not the owner.
- Trigger handlers:
  - No event, {}, an empty uid and a guessed uid each do nothing, and only the fixed log lines appear.
  - The uid of the other handler's trigger is refused.
  - Real trigger uids run.
  - A helper's page call does nothing.
- Other handler tests now fire with a real trigger event.

## Post-release fix D-12

Bug: under Execute as Me and Only myself, the web app reports a blank active user, so `ibOwner_` refused the owner
("Not allowed").
Change (apps-script/Inbox.gs `ibOwner_`): it reads three addresses, each trimmed and lower-cased, with any error or null
counted as blank: the Song Database owner (getActiveSpreadsheet().getOwner()), the effective user and the active user.
It allows only when the owner and the effective user are non-empty and equal, AND the active user is '' or equals the owner.
It refuses with messages that name the failed part and contain no address:
- "Not allowed: the Song Database owner could not be read (is it on a Shared Drive?)"
- "Not allowed: the admin app must be deployed as Execute as: Me" (effective user blank or not the owner, e.g. helper mode)
- "Not allowed: you are signed in as a different Google account than the Song Database owner"
Tests (tests/unit/test_inbox.js):
- Allowed: the owner with a blank active user (the real web app case), and the owner with a matching active user in any case.
- Refused, each with its exact message on all 9 functions, with nothing written, no mail and no address logged:
  - a different signed-in account
  - FS_NOTIFY when it is not the owner
  - helper mode
  - a blank active user with a non-owner effective user
  - a blank effective user
  - a blank, null or throwing owner
docs/SETUP.md section 11: added the warning "Keep the deployment as it is": Execute as: Me and Who has access: Only
myself, and why. With Anyone access, strangers often show a blank active user and would reach the Inbox.
Residual risk, for security: the blank-active branch means the screen check alone no longer stops a stranger if the
deployment is ever widened to Anyone while it runs as Me. "Only myself" is now the control that matters, and it is
documented. NF-02 trigger-event checks are unchanged.
